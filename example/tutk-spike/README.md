# Tutk Wyze Protocol Spike (Phase 0)

Pure-JavaScript port of the **Tutk Wyze IOCtrl protocol** — the
control-plane commands used by every non-Gwell Wyze camera (V2, V3,
V4, Pan v1/v2/v3, Outdoor / Outdoor 2, original Doorbell, OG, Battery
Cam Pro, Robot Vacuum) when talking over Throughtek's IOTC channel.

**Status:** Phase 0 protocol primitives, validated against the reference
Python implementation in
[docker-wyze-bridge](https://github.com/mrlt8/docker-wyze-bridge).

The protocol modules originally lived here under `lib/`. They have been
promoted into the package's main source tree at
[`src/tutk/lib/`](../../src/tutk/lib/) and are used by `src/tutk/session.js`.
This directory now keeps only the demo (`spike.js`) and fixture tests as
runnable documentation of the protocol layer in isolation.

## What's in this directory

```
tutk-spike/
├── spike.js               End-to-end protocol round-trip + perf bench
├── test/
│   └── fixtures.test.js   Pinned vectors vs Python reference
└── README.md              you are here
```

The actual modules (imported above) live in `src/tutk/lib/`:

- `constants.js`  Protocol version 5, prefix "HL", FRAME_SIZE, BITRATE
- `header.js`     16-byte TutkWyzeProtocolHeader pack/unpack
- `codec.js`      encode(code, data) + decode(buf) top-level helpers
- `messages.js`   All 63 K-classes (K10000 … K12060)
- `xxtea.js`      XXTEA cipher (used in auth challenge-response)
- `auth.js`       generateChallengeResponse + buildAuthResponse

## Running

```bash
# Individual self-tests (each module, run from src/tutk/lib/):
node ../../src/tutk/lib/xxtea.js

# Top-level spike — round-trips everything:
node spike.js

# Fixture vectors pinned against Python reference:
node test/fixtures.test.js
```

Each script exits 0 on success, 1 on failure.

## Cross-language verification

Every fixture in `test/fixtures.test.js` was generated by running
docker-wyze-bridge's Python against the same inputs. JS output is
**byte-exact** for:

- 8 K-class encodings (K10000 empty, K10000 with mac, K10042 NV,
  K10092 set-time, K10052 bitrate, K10056 resolving, K10302 timezone,
  K11000 rotary)
- 3 XXTEA encrypt vectors (8B with two different keys + 32B)
- 1 XXTEA-based challenge-response (status=3 path)

To re-verify yourself:

```bash
pip install xxtea
python3 -c "
import struct
def encode(code, data):
    data = data or b''
    return struct.pack(f'<BBHHH8x{len(data)}s', 72, 76, 5, code, len(data), data)
print(encode(10042, bytes([3])).hex())
"
# → should match the K10042 hex in fixtures.test.js
```

## What works

- ✅ 16-byte header pack/unpack (`HL` + protocol + code + txt_len + reserved)
- ✅ `encode(code, data)` and strict `decode(buf)` matching dwb's reference
- ✅ All 63 K-class message types — auth, video config, OSD, time,
  motion, PTZ, cruise, accessories, floodlight, etc.
- ✅ Response parsers — JSON, uint32 timestamp, success-byte, custom dicts
- ✅ XXTEA (encrypt + decrypt) matching pyxxtea byte-for-byte
- ✅ `generateChallengeResponse` for all three auth paths
  (status=1 legacy, status=3 standard, status=6 doorbell)
- ✅ `buildAuthResponse` — picks K10002/K10006/K10008 by model + protocol
- ✅ Performance: ~1M encode/decode ops/sec, ~1M xxtea 16B encs/sec

## What does NOT work yet (Phase 1+)

- ❌ Loading `libIOTCAPIs_ALL.so` via koffi (needs Bionic shim — Phase 1)
- ❌ Live IOTC session establishment against a real camera (Phase 1)
- ❌ A/V transport — actual video frame decode (Phase 2, needs the `.so`)
- ❌ IOCtrlMux orchestration (threading model, response routing) —
  doesn't matter for the protocol layer; that's an integration concern

## Why no IOCtrlMux port?

docker-wyze-bridge's `tutk_ioctl_mux.py` (~300 lines) handles:
- Threading: a background listener pumps responses into futures
- Response routing: matches incoming messages to outstanding requests
  by `expected_response_code`
- Lifecycle: connect, send, close

None of that ships protocol bytes — it's caller-side orchestration on
top of `tutk.av_send_io_ctrl()` (which is in the `.so`). When we wire
this code into the bridge, we'll write our own JS orchestrator
(probably Promise-based, not thread-based) that calls into the
koffi-bound `.so`. The K-class layer is the protocol; the mux is
delivery plumbing.

## Source attribution

Every implementation in this directory is a port of code in
[docker-wyze-bridge](https://github.com/mrlt8/docker-wyze-bridge):

- `src/tutk/lib/header.js` ← `app/wyzecam/tutk/tutk_protocol.py` (TutkWyzeProtocolHeader)
- `src/tutk/lib/codec.js`  ← `app/wyzecam/tutk/tutk_protocol.py` (encode/decode)
- `src/tutk/lib/messages.js` ← `app/wyzecam/tutk/tutk_protocol.py` (all K-classes)
- `src/tutk/lib/xxtea.js` ← XXTEA spec; verified against `xxtea` PyPI package
- `src/tutk/lib/auth.js` ← `app/wyzecam/tutk/tutk_protocol.py`
  (respond_to_ioctrl_10001, generate_challenge_response)

Constants and bitrate enums come from `app/wyzecam/tutk/tutk.py`.

## What Phase 0 proves

If you ran every script in this directory and got "ALL GREEN":

> The JS port of the Tutk Wyze protocol layer produces wire bytes
> identical to the reference Python implementation. We can construct
> every documented Wyze camera command (K10000–K12060), decode their
> responses, and complete the XXTEA-based auth challenge in pure JS —
> with no native code, no .so dependencies, on any OS.

That's the foundation. Phase 1 (`.so` loading + Bionic shim) is what
turns this into real device traffic. Phase 2.5 (wiring K-classes into
wyze-api's helpers) is what gives the bridge sub-second device
control instead of cloud round-trips.

## Phase 0 is NOT shipped to npm

Like `gutes-spike/`, this directory lives under `example/` and is
excluded from the published package via `package.json`'s `files`
field. It exists for development + manual verification only. When
this matures into something users run, the relevant code moves to
`src/tutk/` with proper exports.

## Hardware coverage

Verified to be the protocol used by **every camera on the maintainer's
account** (8 cameras across 5 models: WYZE_CAKP2JFUS / WYZEDB3 /
WVOD1 / WYZECP1_JEF / WYZEC1-JZ) — that's why we ported Tutk in
parallel with GUTES even though the GUTES port (cryze, for Doorbell
Pro) was done first. Most of the Wyze camera lineup is on Tutk.

The Robot Vacuum (JA_RO2) also rides the Tutk stack — same K-class
catalog (different command IDs for vacuum-specific actions, but the
header + auth + transport are identical).
